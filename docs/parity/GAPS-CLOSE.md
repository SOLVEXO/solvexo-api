## 2. P8 gaps: DONE in code; verified on a real local Mongo + live over HTTP
- New webhook topics now fire from schema hooks (every write path, no service edited): `product.updated` (any real product write; view/rating counters ignored), `inventory.changed` (stock on-hand / reservation / damaged / in transit / expired moved; payload on_hand, committed, available), `customer.created` (store customers only: guest sessions and other stores excluded), `refund.created` (one event per refunded AMOUNT: each partial refund raises the running total, plus the full refund). Bursts of writes to one record are coalesced (1.5 s) and keyed per 30 s bucket; every delivery is routed by the record's OWN store and signed like the order events.
- Write API (`api/merchant/v1`): `PATCH products/:id` (status, tags only: an allow-list) and `POST inventory/adjust` (relative change through `InventoryService.adjustStock`, so location rows and the history row stay right). Both need an explicit `write_*` scope (a read token gets 403) and an `Idempotency-Key` header; the same key + same body returns the stored answer (`Idempotent-Replayed: true`) and has ONE effect; the same key with another body is 422; a failed attempt does not burn the key; keys expire after 24 h. Only the token's own store is reachable (another store's product/variant is "not found"). Each write is audited as actor `api_token`.
- Live check (API on the throw-away stack): read-only token refused, no key refused (400), replay and key reuse (200 / 422), stock +5 applied once (200 -> 205 with the same key sent twice), product.updated / inventory.changed / customer.created deliveries queued.
- BUG found on the way and fixed: the activity-log schema enum rejected the categories `khata`, `webhooks`, `api_tokens`, `api_token` and `b2b`, so audit entries written by the Khata, webhook/API-token and B2B code were silently dropped (only a server log error). Added the categories + a test that scans these modules for unknown categories (`activity-categories.spec`). Entries written before this fix are lost.
- Tests: `merchant-api.gaps.spec` (hooks matter-rules, topics routed per store + signature, refund per amount, idempotency, isolation, validation, audit call) with the existing P8 specs: 33 pass; permission-coverage passes.
- Not done: write endpoints for customers / orders; customer.created for customers created before webhooks existed; delivery of these topics through real Redis queue (the DB-backed cron is unchanged).

## 3. P12 gaps: DONE except POS PIN (documented); verified over HTTP on the throw-away stack and in Chrome
- **Step-up on password change:** seller `PUT api/users/change-password` and staff `PUT api/staff/me/password` now need a fresh code (`x-step-up`) when the person has 2FA (403 `STEP_UP_REQUIRED`; the web client asks for the code and retries, as for the other protected actions). Verified: seller change without step-up -> 403. **There is no email-change endpoint** (profile edit does not allow email), so there is nothing to protect there.
- **Reset 2FA button:** Staff page (owner only, shown only for people who use 2FA) -> confirm dialog -> `POST api/2fa/store/:storeId/staff/:staffId/reset`, audited. Owner-only `GET api/2fa/store/:storeId/policy` lists who has 2FA. Verified: owner reset 201, a staff member trying to reset anyone 403.
- **"Require 2FA for staff" now really blocks:** Store settings `requireStaffTwoFactor`, `staffTwoFactorGraceDays` (0-30, default 7), `requireStaffTwoFactorSince` (set when the policy is switched on). `PermissionsGuard` refuses every permission-guarded route for a staff member without 2FA once the grace period is over (403 `TWO_FACTOR_REQUIRED`); the 2FA setup, profile and security routes carry no permission guard so setup stays reachable. The verdict is cached per person for up to 60 s per API instance and cleared at once on policy change / enable / disable / reset. Web: Security page switch + grace-days field + "blocked from <date>" line; a blocked staff member is sent to their Security page. Verified live: staff opens orders (200) -> owner switches policy on with grace 0 -> 403 TWO_FACTOR_REQUIRED -> setup reachable (201) -> after enabling 2FA orders work again (200). Not covered: other API instances keep an old verdict for up to a minute; the owner is never blocked.
- **QR image:** drawn in the browser from the setup link with the `qrcode` package already in the web app (no outside service). Verified in Chrome: image present as a data URL next to the setup key and the "Open in my authenticator app" link.
- **Google sign-in (sellers):** a seller with 2FA who signs in with Google now gets the same code step instead of a session (before this the code step was bypassed by Google sign-in). Backend returns the challenge (live check not run: needs a real Google token); web: `useSocialLogin` hands the challenge to the login page's code form. Apple sign-in goes through the same `socialLogin` method. Customer (buyer) social login is a different system and has no 2FA.
- **POS PIN: NOT implemented, on purpose.** A POS employee signs in with a 4-digit PIN on a shared till (token type `pos_employee`); they are neither seller nor staff accounts, and a TOTP code needs a personal phone per cashier, which does not fit a shared terminal. CORRECTION: the PIN lockout already existed (5 wrong PINs lock the employee for 15 min and end their open sessions, audited as `pin_locked`; a per-device limiter returns 429; the owner's reset-PIN clears the lock); the CLAUDE.md note that it was missing is outdated. 2FA is still not the right tool for a shared till.
- Tests: `staff-two-factor-policy.spec` (6: policy off, grace, block, grace 0, owner, cache clear), member-two-factor and permission specs still pass. Lint: LoginPage keeps two old `autoFocus` warnings (not from this change).
