# Q3 Fulfilment services / 3PL (implemented + tested at real-Mongo level; no real 3PL, no browser)

## What exists
- **Registry** (`src/fulfillment-services/`): `FulfillmentService` per store (max 5; provider `generic_http` signed HTTPS or `mock`; secret AES-GCM, shown once, rotate; `autoRoute`; `trackInventory`). Connecting creates an owned **warehouse location** (`StoreLocation.fulfillmentServiceId`).
- **Provider interface** (`fulfillment.util.ts`): `send(ctx, payload)`; generic adapter = POST with `X-Solvexo-Signature: t=..,v1=..` (same scheme as webhooks), public https hosts only, DNS re-checked, no redirects, 10 s timeout; mock adapter never uses the network. Callback field names live only in `parseCallback` (unknown vendor shapes: map there, see OPEN-QUESTIONS).
- **Routing**: seller "Send order" (order detail card + `POST requests`) or `autoRoute` (paid orders, hooked on the existing order-changed event, once per order via unique `{store,order,service}`). Request = physical unshipped lines of THIS store, address, shipping method.
- **Queue** `fulfillment-send` (4 attempts, exponential backoff); `processSend` is idempotent (claims `pending`), throws before the last attempt, records `failed` on the last; seller can retry/cancel.
- **Signed callbacks** `POST api/fulfillment-callbacks/:serviceId` (HMAC of the raw body; unknown service and bad signature give the same 401): `accepted`, `shipped` (+tracking -> existing `OrdersService.fulfilItems`, buyer email/stock rules unchanged; if fulfilling fails the event is undone so the retry works), `delivered`, `cancelled`, `stock`. Idempotent per `eventId`, forward-only status, cancel refused once shipped, a service can only touch ITS store's requests.
- **Stock sync**: `stock` rows `{sku, quantity}` set the owned location row and move `ProductVariant.stock` by the difference; unknown SKUs skipped and counted; other stores' SKUs never touched.
- **Seller UI**: Inventory -> **Fulfilment** tab (connect, switch on/off, new secret, auto-send switch, remove, callback address, requests log with status filter/paging, retry, cancel) + "Fulfilment service" card on order detail.
- **Permissions** `fulfillment.view` / `fulfillment.manage` (staff registry api+web, preset version 5: Store Manager both, Support view). **Audit** category `fulfillment` (connect/update/rotate/remove, request created/auto/retried/cancelled, callbacks).

## Tests run
- `fulfillment.integration.spec.ts` (real Mongo, direct processor/service calls): 14 tests (pure transitions/parsing, connect + location, tenant isolation, request build/duplicate/digital, send success/redelivery/failure/retry, signature failures, accepted -> shipped -> fulfil once, forward-only, fulfil failure undo, cross-store callback, stock sync, auto-route, remove/cancel). `permission-coverage`, `activity-categories` specs pass. Web `FulfillmentTab.test.tsx` 4 tests. API + web `tsc` clean.

## NOT verified / limits
- No real 3PL, no real Redis/BullMQ worker, no browser. `delivered` only updates the request (the order is marked delivered by the seller as today). `cancelled` from the service only marks the request (the seller decides about the order). Partial shipments by a service are shipped as the whole request quantity. Seller UI strings are English (seller dashboards are not translated); no customer-facing text was added.
- Needs the 3PL's real payload/signature scheme mapped in `fulfillment.util.ts` before a vendor can be connected.
