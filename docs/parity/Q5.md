# Q5 Checkout rules (Functions-lite) + checkout branding (implemented + tested at real-Mongo / unit level; no browser, no real checkout run)

## Rules (declarative JSON, server-side, no code execution)
- **Storage/limits** (`src/checkout-rules/`): `CheckoutRule` per store, max 50 rules, max 8 conditions per rule, lists <= 20 values, message <= 200 chars, priority 0-1000 (lower first, ties by id), `active` / `draft`. Type can never change after creation. Products named in a rule must belong to the store.
- **Whitelist**: fields subtotal, itemCount, lineCount, maxLineQuantity, country, city, state, postalCode, productIds, customerTags, isB2B, isGuest, hasDigital, hasPhysical; operators per field kind (number eq/neq/gt/gte/lt/lte, string eq/neq/in/not_in/starts_with, set contains/not_contains/contains_any, boolean eq). Values are strings/numbers/booleans/string lists only (objects such as `{$gt:1}` are refused). Unknown address parts never match.
- **Actions**: (1) `discount` percent/fixed on the order or on chosen products, `exclusive` (first match wins, default) or stackable, total capped at the cart subtotal; address fields are refused for discount rules. (2) `payment` hide / show_only by method key (stripe, cash_on_delivery, split, manual_bank_transfer, b2b_terms, manual, or a gateway key). Hide beats show-only; two show-only rules intersect; no fail-open (the same function decides what is offered and what is accepted). (3) `shipping` hide / rename / move to top, by zone id or zone type; hiding everything is ignored. (4) `validation` blocks with the seller's message (max quantity, restricted region, customer tag, B2B, guest...).
- **Where it runs** (same `evaluate`): `createCheckout` (cart discounts distributed over the item totals through the existing proportional helper, validation blocks, `Checkout.ruleDiscountTotal/Labels`); checkout `allowedPaymentMethods`; seller-gateway list (`listPaymentMethods`); `getShippingZones` (hide/rename/reorder for the buyer's cart + default address); `addShippingInCheckout` (blocks + hidden delivery option refused); `PaymentService.assertDiscountsStillValid` (blocks + hidden payment method refused at EVERY payment entry, so the UI cannot be bypassed). Buyer cart preview: `GET api/checkout-rules/storefront/preview`.
- **Seller**: Orders group -> **Checkout rules**: Rules (plain-words list, builder modal, turn on/off, delete), "Test a cart" (sample cart, drafts optional, shows discount / blocked / payment methods left / delivery options left), Checkout branding. Permissions `checkout_rules.view/manage` (staff registry api+web, preset v7). Audit category `checkout_rules`.

## Checkout branding
`Store.checkoutBranding {logoUrl (https), accentColor (#rrggbb), footerLinks[<=5] (https or /site-path)}` validated by `store/checkout-branding.util.ts`, saved through `update-store`, public in the storefront store payload. Maison, Tech and Ledup checkout show the logo bar on top and the footer links at the bottom (`core/checkout/CheckoutBranding`); the accent colours links, checkboxes/radios and focus rings only (theme buttons keep the theme colour). No branding set = every theme looks as before.

## NOT verified / limits
- `createCheckout` / `addShippingInCheckout` / `getShippingZones` wiring is type-checked and covered through the service-level enforcement tests, but NOT run through a real full checkout on Mongo/Stripe or a browser. Discount rules cannot use address fields. Rule amounts use the same unit as automatic discounts. The cart preview endpoint exists but no theme shows it yet. Rule messages are written by the seller (not translated); no new en/ur storefront keys. Branding accent does not recolour theme buttons. Gateway keys other than the listed methods have to be typed by key (no picker). Product conditions use product ids (picker only for discount products).
