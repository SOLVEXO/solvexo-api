# Q6 A/B experiments (Rollouts-lite) — implemented + tested at real-Mongo / component level; no real traffic, no browser

## What exists
- **Experiment** (`src/experiments/`): per store, max 10 (max 3 running, one running per section, one running theme test). Two versions only: **A = the current look**, **B = plain overrides**. Kind `section` (overrides on ONE section's settings, by section id) or `theme_settings` (overrides of `custom.*` theme settings). Overrides are plain values only (text without `<`/`>`, numbers, yes/no; <= 20 keys; `type`, `blocks`, `enabled`, `colorSchemeId`, `customCss`, `html`, operator-like and dotted keys refused). Statuses draft -> running <-> paused -> stopped; only a draft can be edited; a running one cannot be deleted. Traffic % (share of eligible visitors) and split % (share of them who see B).
- **Bucketing** (`experiments.util.ts`): sha256 of `salt:experimentId:visitorId` -> stable number in [0,100); one hash decides entering, a different one decides A/B, so raising the traffic never drops or moves anyone. The visitor id is the existing random analytics id (`sx_vid`); **a visitor who did not allow analytics has none and is never in a test** (consent respected). No personal data is stored.
- **Assignment** `GET api/public/experiments/:storeId/assignments?visitorId=` (anonymous, throttled, behind the password-store gate): running tests -> `a`/`b` for that visitor; an applied winner B is returned to EVERYONE (even without a visitor id). **Exposure** `POST .../exposure {sessionId, visitorId, experimentId}`: the server recomputes the variant (the browser cannot choose it) and writes `{experimentId, variant}` once on that visit (`StorefrontSession.experiments`, additive field).
- **Goals = the existing server-side funnel flags of the visit** (`addedToCart`, `reachedCheckout`, `converted`): nothing new is sent from the browser, so a goal cannot be faked. Unit = a visit (session). A converted visit that never joined the test is not counted.
- **Results + significance**: `GET api/experiments/:storeId/:id/results` = per variant visits / added to cart / reached checkout / orders / conversion %, plus a verdict on orders (two-proportion z-test): `not_enough_data` (< 100 visits per version or < 10 orders in total), `inconclusive`, `leaning` (p < 0.2), `likely` (p < 0.05) and which version leads.
- **Winner**: stop the test, then "Use B for everyone" (B's overrides keep being applied at render time to every visitor; the section itself is NOT rewritten, so it is reversible) or "Keep original". Can be picked once.
- **Storefront**: every theme's section renderer (Maison, Tech, Ledup) calls `useExperimentSections` (variant B settings merged into the matching section; never in the editor/preview) and reports the exposure after 1.5 s (retry once after 4 s, because the page view creates the visit first). `StorefrontLayout` loads the assignments (re-loaded when analytics consent changes), merges theme-setting overrides into `theme.theme.themeSettings` and reports their exposure. Any failure leaves the normal store.
- **Seller UI**: Orders group -> **Experiments** (`/store/:id/experiments`): list with status, create/edit modal (page + section picker that offers only the plain settings of the chosen section, tick what changes in B, traffic and split), Start / Pause / Resume / Stop (confirm), Results modal with plain-language verdict, Use B for everyone / Keep original, Delete. Permissions `experiments.view/manage` (staff registry api+web, preset v8). Audit category `experiments`.

## Tests run
- `experiments.integration.spec.ts` 14 tests (real Mongo): stability / traffic + split shares over 20,000 visitors / monotonic traffic increase / independence between experiments; override + experiment validation; z-test + verdicts; tenant isolation; draft-only edit and conditional transitions; limits; assignments (no visitor id, other store, paused); exposure (server-chosen variant, once, wrong visitor/store/experiment refused); results count only exposed visits; winner b served to everyone, winner a not. `permission-coverage`, `activity-categories`, `storefront-access`, `storefront-analytics` specs pass. API `tsc` clean.
- Web: `experiments.test.tsx` 5 (overrides merge rules, exposure timing/once/not in editor, no visitor id without consent, failure fallback), `ExperimentsHub.test.tsx` 6; `src/features/storefront*` 51 files / 299 tests pass; `tsc -b` and eslint clean on the new files.

## NOT verified / limits
- No real visitors, no real cookie banner consent flow, no browser. Flicker: the assignment is fetched after the first paint, so a visitor in B may briefly see A first. "Section id" targets one section; a section that is not on a page is just never changed. Only two versions (A/B), no multi-variant, no theme-swap (a "theme variant" here means theme settings). Orders are counted per visit, not per visitor; funnel flags can be set before the exposure in the same visit. Winner B is applied at render time and is not baked into the section. No cart-page/mini-cart exposure for tests on sections that only render there beyond what the renderer reports.
